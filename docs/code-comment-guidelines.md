## TypeScript 注释规范

### 1. 基本原则

- 注释使用简体中文，技术术语、API 名称、协议字段和标识符保留原文。
- 注释必须提供代码本身无法直接表达的信息，包括设计原因、业务约束、边界条件、并发语义和异常处理策略。
- 禁止逐行翻译代码，禁止重复函数名、参数名、返回类型等显而易见的信息。
- 禁止为了显得专业而增加注释。没有必要时，不写注释。

### 2. 注释类型

- 模块注释：说明模块的职责、边界及关键约束。
- 导出 API 的 JSDoc：说明用途、重要前置条件、可观察行为及异常语义。
- 实现注释：仅解释复杂逻辑的原因、算法不变量或特殊处理。
- 临时兼容注释：说明兼容原因、影响范围和可验证的移除条件。

### 3. 长度与拆分

- 类或模块的概述原则上不超过 5 行。
- 普通函数的 JSDoc 原则上不超过 8 行。
- 注释超过 10 行时，必须检查是否混入了多个职责；确有必要时拆分为分节注释、方法注释或独立架构文档。
- 上述行数是审查阈值，不是机械截断规则。复杂协议和安全约束允许保留必要的详细说明。

### 4. JSDoc 格式

- 使用标准 `/** ... */` 格式。
- 只为有文档价值的导出 API 编写 JSDoc；私有方法按需注释。
- TypeScript 已经表达的类型不重复写入 `@param`、`@returns` 类型声明。
- 参数含义、非显然的返回语义和重要异常行为确有必要时，使用相应标签。
- 多条独立约束使用列表或分节，不要将整段内容写成一个长段落。

### 5. 准确性与维护

- 不得编造代码中不存在的行为、调用关系、业务规则或保证。
- 修改代码时，同步检查受影响的注释。
- 不确定的设计意图应先查阅实现、测试和架构文档；仍无法确认时，向用户提问，不得自行猜测。
- 注释必须与当前实现一致，不得保留过期的变量名、调用流程或行为描述。

### 6. 完成任务前的自检

检查以下事项：

1. 是否存在重复代码含义的注释？
2. 是否把多个方法的实现细节堆在一个类注释中？
3. 是否遗漏关键业务约束、失败语义或并发条件？
4. 是否存在与实现不一致的描述？
5. 是否能通过重命名、拆分方法或提取常量，让代码本身更清晰？
6. 是否需要更新架构文档，而不是继续扩展代码注释？

仅修改受本次任务影响的注释，不要无关地重写整个文件的注释。
