# AI 开发流程规范（给 AI agent 参考）

适用项目：aimi（`apps/server`、`apps/mobile`、`packages/protocol`）。
本文档规定 AI agent 在新增功能、修改功能、修复 bug、重构等任务中必须遵循的流程。
你的产出会经过自动化门禁和人工审核：**自动化拦下有明确对错标准的问题，人工只看业务意图、架构和高风险逻辑。**
命令以仓库实际的 `package.json` 为准，若与本文不一致，以仓库为准并在汇报中指出。

---

## 一、总原则

1. **不直接改 `main`**。一个任务一个分支，分支名：`feat/xxx`、`fix/xxx`、`refactor/xxx`、`chore/xxx`、`docs/xxx`、`hotfix/xxx`。
2. **一个 PR 只做一件事**，改动控制在 400 行内；超出须拆分，或先停下来问人。
3. **先测试，后实现**。测试依据需求和验收标准编写，不得迎合已写好的实现。
4. **最小改动**。只改完成任务所需的代码，不顺手重构、不改格式、不动无关文件。
5. **复用优先**。先搜索现有工具函数和模式，不重复造轮子；新增依赖须先说明理由并等待确认。
6. **不确定就问**。需求有歧义、有多种合理方案时，先列出方案和取舍，不要自行猜测。
7. **如实汇报**。检查没跑、用例失败、做过的假设都必须明确写出，禁止写"应该能通过"。
8. **不编造**。不确定某个 API、库用法是否存在时，查看项目现有代码或官方文档，并说明不确定之处。

---

## 二、通用流程（所有任务适用）

```
理解需求 → 出方案（复杂任务）→ 开分支 → 先写测试 → 实现 → 本地检查
→ 自查清理 → 提交 → 开 PR（填模板）→ CI → 独立审查 + 人工审核 → squash 合并
```

### 步骤说明

| 步骤 | 要求 |
|---|---|
| 1. 理解需求 | 复述需求、改动范围、验收标准（"做到什么算完成"）。有歧义先提问 |
| 2. 出方案 | 复杂任务（跨模块、改接口、改数据结构、预计 >200 行）先只出方案、不写代码，等确认 |
| 3. 开分支 | 从最新 `main` 拉分支，命名见上 |
| 4. 先写测试 | 把验收标准转为测试，含正常路径、边界值、空值、异常输入、错误处理；确认测试在实现前失败 |
| 5. 实现 | 最小改动，通过测试 |
| 6. 本地检查 | 见第四节，必须全部通过 |
| 7. 自查清理 | 见第五节 |
| 8. 提交 | 小步提交，信息格式：`type(scope): 简述`，如 `fix(session): 修复重连后状态丢失` |
| 9. 开 PR | 按 PR 模板填写（见第六节） |
| 10. 合并 | CI 全绿且审核通过后 squash merge；**由人决定合并**，agent 不自行合并 |

## 三、按任务类型的流程

### 3.1 新增功能（feat）

1. 写清验收标准；复杂功能先出设计方案，确认后再动手。
2. 大功能拆成多个可独立合并的小 PR（如：protocol 定义 → server 实现 → mobile 界面 → 联调），每个都可单独验证。
3. 先写测试再实现。
4. 涉及 protocol 的改动：同步更新 zod schema 与 mobile `frame_dto`，并确保双侧契约测试通过。
5. 影响线上行为的功能，评估是否需要开关（feature flag）或灰度。

### 3.2 修改已有功能（feat / refactor）

1. **先补保护再改**：现有行为若缺少测试，先补"特征测试"固定当前行为，再修改。
2. 明确哪些行为会变、哪些必须不变，写进 PR 描述。
3. 关注兼容性：接口、协议帧、数据格式、数据库结构变更须考虑旧版本客户端和数据迁移——这类属于高风险，必须停下来请人确认。
4. **重构与功能改动分开提 PR**，重构必须保持行为不变且有测试保护。

### 3.3 修复 Bug（fix）

1. **先复现**：写一个能稳定复现 bug 的失败测试，并确认它确实失败。
2. **找根因**：解释为什么会出这个 bug，禁止只"改到不报错"（吞异常、加 try/catch 掩盖、放宽断言都不算修复）。
3. 修复后确认：新测试变绿，原有测试不受影响。
4. 排查同类问题：同一根因是否在其他位置也存在，列出但不要擅自扩大改动范围。
5. PR 描述必须包含：现象、根因、修复方式、回归测试。
6. **线上紧急问题（hotfix）**：从线上版本分支拉 `hotfix/xxx`，最小改动，仍须经过 CI，不得绕过门禁；合并后同步回主线。

### 3.4 重构（refactor）

- 前提：行为不变，且受影响代码已有测试保护（没有则先补，单独提交）。
- 不夹带功能改动、不修 bug；发现 bug 记录下来另开任务。
- 不改变公共接口；确需改变则停下来问人。

### 3.5 依赖升级（chore）

- 单独 PR，不混其他改动。
- 阅读 changelog，关注破坏性变更；跑全量测试（L1 + L2）。
- 不引入未经确认的新依赖。

### 3.6 文档 / 配置 / 样式（docs / chore）

- 低风险，自动化通过即可。
- 但**门禁相关配置**（见第七节）不属于"低风险配置"，不得顺手修改。

### 3.7 探索 / 实验

- 在临时分支尝试，不直接合并探索代码；结论有价值后，在干净分支上重新实现。

## 四、本地检查（提交/推送前必须通过）

> 命令为方案约定，落地后以仓库实际脚本为准。

| 检查 | 命令（参考） | 说明 |
|---|---|---|
| 格式化 + Lint | pre-commit 自动执行（prettier、eslint，仅暂存文件） | 不得绕过 |
| 密钥扫描 | `node tools/check-secrets.mjs` | 不得提交密钥、token、`.env` |
| 类型检查 | `pnpm -r typecheck` / `tsc --noEmit` | |
| 依赖检查 | `node tools/check-deps.mjs` | |
| 单元测试（L1） | `pnpm --filter <pkg> test:unit` | 受影响范围必跑 |
| 集成/e2e（L2） | `pnpm --filter ./apps/server test:e2e` | 涉及 server 核心链路、协议、会话时必跑 |
| 覆盖率 | `node tools/check-coverage.mjs` | 全局不得低于 baseline；新增/修改行覆盖：server/protocol ≥80%，mobile ≥60% |
| mobile | `flutter analyze` + `flutter test`（按仓库实际） | 改动 mobile 时必跑 |

要求：
- 检查失败必须找到**根因**并修复，不得靠重试、吞异常、跳过来掩盖。
- pre-push 有 60s 超时熔断，熔断时会提示"检查未完成，降级为仅 CI 验证"——此时应主动在本机补跑完整检查，不能默认通过。

## 五、自查与清理（交付前必做）

1. 运行 `git status --short`，确认**只有与任务相关的改动**。
2. 测试截图、日志、报告、缓存等临时产物：
   - 只能输出到系统临时目录（`$TMPDIR` / `/tmp`），不得写入源码目录；
   - 确需留档的放 `docs/assets/` 并显式 `git add`；
   - 若工具必须使用 `.omx/` 等工作目录，确认其已在 `.gitignore`，未忽略则先添加规则并在汇报中说明。
3. 任务结束前删除自己生成的所有临时文件。
4. 禁止出现在提交中的内容：`*.png`（根目录截图）、`*.env`、`.omx/`、`.zcode/`、`*.log`、`coverage/`、`plugins/token-speed/`、任何密钥或含敏感信息的文件。
5. 检查 diff：是否包含无关格式化、无关重构、调试代码（`console.log`、`debugger`）、注释掉的代码。

## 六、PR 要求

PR 描述必须包含（对应 PR 模板字段）：

1. **改了什么、为什么**
2. **验收标准与验证方式**：跑了哪些命令、结果如何（贴真实输出，不得概括为"已通过"）
3. **测试变更说明**：新增/修改的测试验证了哪些行为、关键断言点；**未覆盖**的场景
4. **风险点与需要人工重点审核的地方**
5. **清理确认**：`git status --short` 输出、已清理的临时文件
6. **门禁变更勾选**：若改动了第七节中的门禁文件，必须说明理由与影响面
7. **高风险自查清单**：若触及高风险路径，逐项填写

规模要求：单个 PR ≤ 400 行；超出须拆分，或说明为何不可拆并请人确认。

## 七、风险分级与审核

| 风险 | 路径 | 要求 |
|---|---|---|
| **高** | `auth/**`、`session/**`、`persistence/sqlite/migrate.ts`、`packages/protocol/src/**`、`bin/**` | 必须停下来说明，人工重点审核；合并前需独立 AI 审查并附结论 |
| **高（门禁自保护）** | `.github/workflows/**`、`tools/check-*.mjs`、`tools/coverage-baseline.json`、`tools/__tests__/`、`eslint.config.*`、`**/vitest.config.ts`、`.husky/**`、`package.json`（scripts/devDeps）、`pnpm-lock.yaml`、`tests.flaky-exclude.txt` | **禁止修改**，除非任务明确要求；修改须在 PR 中勾选并说明理由 |
| 中 | `agents/claude/**`、`transport/**`、`ops/**`、mobile `data/` 层 | 常规审核，重点检查边界与错误处理 |
| 低 | `ui/**`、文档、普通配置 | 自动化通过即可 |

## 八、禁止事项

- 禁止删除、跳过、注释、弱化现有测试（`skip`、`xfail`、放宽断言、缩小覆盖范围）。
- 禁止修改 CI 配置、lint 规则、覆盖率阈值与 baseline、coverage `exclude`、husky 钩子来让检查通过。
- **baseline 只能由维护者单独提交上调，agent 不得下调。**
- 禁止使用 `--no-verify`、`--force`、`git reset --hard`、`git push -f` 等绕过检查或破坏历史的操作。
- 禁止直接推送 `main`，禁止自行合并 PR。
- 禁止顺手重构、批量格式化、改动无关代码。
- 禁止编造 API、库函数、配置项。
- 禁止提交密钥、`.env`、个人信息、含敏感信息的截图。
- 禁止用"重试到通过"处理不稳定测试；发现 flaky 测试应记录并报告，不得自行加入隔离清单。

---

## 九、必须停下来交给人判断的情况

遇到以下任一情形，**停止动作，说明情况并等待指示**：

1. 需求有歧义，或存在多种合理实现方案
2. 任何门禁检查失败且无法定位根因
3. 需要下调覆盖率 baseline 或阈值
4. 需要修改或删除现有测试才能继续
5. 涉及高风险路径的语义变更（认证、权限、会话、数据库迁移、协议帧）
6. 需要新增依赖、修改公共接口、修改数据库结构
7. 需要修改门禁相关文件
8. 预计改动超过 400 行
9. 需要执行破坏性操作（删除数据、重写历史、强推）
10. 发现业务代码中与当前任务无关的 bug（记录并报告，不要顺手修）

## 十、交付汇报格式

任务完成后按以下结构汇报：

1. **改动摘要**：改了什么、为什么
2. **改动文件清单**
3. **验证结果**：每项检查的命令与真实输出（未运行的检查须明确标注"未运行"及原因）
4. **新增/修改的测试**：覆盖了哪些场景，未覆盖哪些
5. **风险点与需人工重点审核的地方**
6. **清理确认**：`git status --short` 输出，已清理的临时文件
7. **假设与未完成/不确定事项**

不得隐瞒失败、跳过的检查或做过的假设。

## 十一、任务启动模板（人类可直接粘贴）

**新增功能**
```
任务：新增 <功能名>
验收标准：1) … 2) … 3) …
范围/约束：<涉及模块、不得改动的部分>
请按 AI-DEV-WORKFLOW.md 的「新增功能」流程执行：先复述需求并出方案，我确认后再写测试和实现。
```

**修改功能**
```
任务：修改 <功能名>，使其 <新行为>
必须保持不变：<旧行为/接口>
请先为现有行为补特征测试，再修改；重构与功能改动分开提交。
```

**修复 Bug**
```
Bug：<现象>，复现步骤：<步骤>
请先写能复现该 bug 的失败测试，定位并解释根因后再修复；PR 中写明现象、根因、修复、回归测试。
```

**重构**
```
任务：重构 <模块>，目标：<目标>
前提：行为不变。先确认测试保护是否充分，不足则先补测试（单独提交）。不得夹带功能改动。
```
